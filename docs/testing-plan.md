## 1. 测试目标

验证 Xjoy MVP 在真实用户手中的表现，重点评估：

- **AI 对话准确性** — RAG 管道是否检索到正确经文？AI 回答是否忠实于原文？
- **阅读体验** — KJV 阅读界面是否清晰易用？
- **整体印象** — 用户是否愿意继续使用？产品的独特价值是否被感知？
- **Bug 发现** — 在真实设备和网络环境中暴露出隐藏的 Bug。

## 2. 目标用户画像

| 画像 | 描述 | 数量目标 |
|------|------|----------|
| 经常读经的信徒 | 每天或每周读经，熟悉 KJV 或中文译本 | 2-3 人 |
| 偶尔读经的信徒 | 一个月读几次，对圣经有基础了解 | 2-3 人 |
| 对圣经好奇的非信徒/慕道友 | 想了解圣经但不熟悉，可能被 AI 交互吸引 | 1-2 人 |
| 技术背景用户 | 对 AI 工具有经验，能从技术角度给出反馈 | 1-2 人 |

**总计目标**: 5-10 人完成反馈表。

## 3. 测试内容

### 3.1 核心流程（必测）

每个用户需要完成以下 5 个任务：

1. **首页体验** — 打开 Xjoy，浏览首页，形成第一印象
2. **阅读经文** — 进入 Reader，浏览至少 2 个不同书卷的章节（建议：诗篇 23 篇 + 约翰福音 3 章）
3. **AI 对话** — 在 Chat 中提出至少 3 个不同类型的问题：
   - 一个事实型问题：「What does the Bible say about love?」
   - 一个解释型问题：「Explain the meaning of Psalm 23」
   - 一个比较型问题：「Compare what Matthew and Luke say about Jesus' birth」
4. **经文搜索** — 使用 Search 功能查找特定经文
5. **深色模式** — 切换深色/浅色模式，在两种模式下阅读

### 3.2 探索任务（可选）

- 尝试连续多轮对话（追问）
- 在移动设备上使用（手机/平板）
- 点击经文引用链接
- 尝试问一个边界问题（如：「What does the Bible say about AI?」）

## 4. 反馈收集渠道

### 4.1 应用内反馈表单（主渠道）

- 用户入口：应用底部导航「反馈」按钮 → `/feedback`
- 管理面板：`/feedback/admin`（查看和分类所有反馈）
- 覆盖 5 个类别：AI 准确性、阅读体验、整体印象、功能建议、Bug
- 支持 1-5 星评分 + 详细文字反馈
- 数据库：Neon PostgreSQL `feedback` 表
- API：`POST /api/feedback`（提交）、`GET /api/feedback?summary=true`（汇总）

### 4.2 直接沟通（辅助渠道）

- 微信/WhatsApp 群聊（针对朋友和家人）
- 电子邮件：用于深度反馈

### 4.3 结构化问卷（辅助渠道）

- 中期提醒（Day 3）：保持参与度，收集初步印象 → `XJO-7-midweek-checkin.md`
- 最终问卷（Day 7）：回顾整体体验，收集推荐意愿 → `XJO-7-exit-survey.md`

## 7. 反馈分类与优先级

### 优先级框架

| 级别 | 标准 | 示例 |
|------|------|------|
| P0 — 紧急修复 | AI 捏造经文、数据丢失、应用崩溃 | "AI 引用了不存在的经文" |
| P1 — 本周修复 | 显著影响核心体验的 Bug | "深色模式下经文看不清" |
| P2 — 下个版本 | 重要但不紧急的功能 | "希望支持书签功能" |
| P3 — Nice to have | 锦上添花 | "能不能加个每日经文推送？" |

### 分类矩阵

| 类别 | 归属 |
|------|------|
| Bug | 功能异常、界面错乱、性能问题 → 创建 Bug Issue |
| 功能建议 | 新功能需求 → 加入产品 Backlog |
| UI/UX 改进 | 交互体验优化 → 加入产品 Backlog |
| AI 准确性 | RAG 管道问题 → 优先处理 |
| 正面反馈 | 记录到学习报告，用于团队激励 |
